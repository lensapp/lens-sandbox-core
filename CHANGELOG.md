# Changelog

All notable changes to `lens-sandbox-core` will be documented in this file.

This project will use versioned releases once public releases begin. Until then, the API should be treated as pre-1.0 and subject to change.

## [Unreleased]

- Initial open-source repository hygiene and contribution documentation.
- Add the `lens-sandbox-runtime` and `lens-sandbox-supervisor` crates, which run a sandbox with no root in the workload.
- Keep an exited exec, with its scrollback and its `exec_exit` / `exec_error`, until the client sends the new `exec_ack` frame or five minutes pass. A reattach to an exited exec gets `exec_attached`, the scrollback, then the final frame.
- Add `ExecManager::detach_for_shutdown` and split `ChildExit` into `Finished` and `Stopped`, so a supervisor can tell a workload exit from a stop signal.
- Bump the protocol date to 2026-10-09.
- The audit dedup folds a failure event only into the same refusal: one with another reason, port, path or caller is sent, so a consumer never files it under the wrong destination.
- A dedup window that folded repeats of a failure event now closes with one summary event: the folded event with `metadata.summary: true`, `metadata.suppressed` (the repeats folded) and `metadata.last_suppressed_at` (when the last of them was refused, RFC 3339), so a consumer can count every refusal. A summary is sent when its window closes, not when the next refusal arrives.
- Add the policy-message field `proxyUpstreamPlainHttp` (`"tunnel"` or `"forward"`). With `"forward"`, the proxy sends a plain-HTTP request to the upstream proxy as a forward-proxy request in absolute form, not through a `CONNECT host:80` tunnel. An absent or unknown value keeps `"tunnel"`.
- Bump the protocol date to 2026-10-13.
- A refused DNS lookup names its caller in `actor.process` (`file.path` and `lineage`), as a proxy refusal does, so a consumer can tell which `binaries` rule refused it. A lookup with no attributable caller, or under a policy with no `binaries` rule, has no actor.
- A refusal or dedup summary the audit channel does not deliver, because it is disconnected or its connection fails before the event is written, is held and sent first when the channel reconnects, so a reconnect no longer loses the refusals it counted. A held refusal is sent as a summary that counts it, dated when it was refused, folded with any later summary of the same refusal. One summary is held per refusal, up to 1024 of them; refusals past that are counted in one summary with `action` and `metadata.reason` set to `audit-overflow`. A refusal from the approval gate (`user-denied-once`, `decision-timeout`, …) is held the same way and is never folded, so each one is counted.
- The proxy door serves an absolute-form `https://` request (`GET https://host/path HTTP/1.1` in the clear, as BusyBox `wget` sends one) instead of closing the socket on it. It is admitted as the `CONNECT host:443` it names, with the same route, card and Always Allow, then judged and relayed by the MITM pipeline, so HTTP rules, credentials, `llm` routes and the audit apply. A request the door cannot read is answered with 400, and a destination the proxy never dials (loopback, link-local, `localhost`) with 403 on every door, instead of a closed socket, and audited as `blocked-destination` as the transparent door audits it.
- An exec can limit its output: with the new `outputWindow` on `exec_attach` and `exec_reattach`, the supervisor sends at most that many output bytes ahead of the client's new `exec_output_credit` frames, so a child that writes faster than the client reads waits in `write` instead of filling memory. The new `exec_release` frame lets a client that goes away keep the exec running, with no limit, for a reattach. An exec with no `outputWindow` has no limit, as before.
- A policy refusal says the sandbox refused it. Every door answers it with `403 Forbidden by sandbox policy`, an `X-Sandbox-Blocked` header carrying the reason (`policy-deny`, `binary-not-allowed`, `ask-declined` or `credential-gate`), `Proxy-Status: sandbox; error=http_request_denied; details="<reason>"`, and a one-line `text/plain` body: `Blocked by sandbox egress policy: GET api.example.com/v1/foo (reason: policy-deny). This is not a response from api.example.com.` An embedder names its product with the new `ProxyState::set_block_label`: with `Lens Agents`, the status reads `403 Forbidden by Lens Agents sandbox policy` and the body `Blocked by Lens Agents sandbox egress policy: …`. The label is set once, and one that is not printable ASCII, is blank or has surrounding spaces, or is longer than 64 bytes is refused. `Proxy-Status` names `sandbox` whatever the label. The body names the method, the host and the path without its query, with any credential placeholder in the path redacted, and nothing else. This covers the plain-HTTP, absolute-form `https://` and transparent HTTP doors, a refused `CONNECT`, a request an intercepted session refuses, and the AWS re-sign path. A destination the proxy never dials is refused the same way, as `policy-deny`.
- Most clients never show the answer to a `CONNECT`, so a `CONNECT` that `egress.http` refuses (`policy-deny`, `binary-not-allowed`, `ask-declined`) is now accepted with `200`: if the client then speaks TLS, the proxy completes the handshake with a sandbox-CA certificate for the `CONNECT` host, reads one request head and answers it with the refusal, so curl, Node, Python and git show it. The destination is never dialled, and the head is not logged; its method and path are audited (see the entry on refused HTTPS requests below). A client that does not start TLS, or sends nothing within 2 s, is disconnected, and the TLS answer is bounded at 10 s. A host no certificate can be made for is refused on the `CONNECT` as before. The transparent TLS door answers a deny, a `binaries` miss or a declined card the same way, inside the session whose SNI it peeked, instead of closing it. A client that does not trust the sandbox CA now sees a certificate error in place of the refused `CONNECT`. An `egress.tcp` refusal, which opts out of interception, a destination the proxy never dials, and a transparent connection without SNI are still refused without TLS.
- A refusal by the upstream proxy is relayed as a block instead of a `502 Bad Gateway`: when the upstream answers a tunnel with `403` and `X-Sandbox-Blocked: upstream-policy`, the client is told with the block response and reason `upstream-policy` — inside the tunnel on the `CONNECT` and transparent TLS doors, in the clear on the plain-HTTP and absolute-form `https://` doors, and inside the session for a host whose token requests the proxy answers. It is audited as a `failure` with status 403. Any other refusal by the upstream is still a 502.
- An intercepted response loses any `X-Sandbox-Blocked` and `Proxy-Status` field the origin sent (a CDN's `Proxy-Status` included), so an origin cannot pass its own answer off as a sandbox block. Interim `1xx` heads (`100 Continue`, `103 Early Hints`) and a `101 Switching Protocols` lose them too; everything else in those heads, the `101`'s `Connection` and `Upgrade` included, is relayed as sent. An `llm` translation writes its own head, so a backend's fields never reach the client either. A response the proxy relays without reading it keeps them: the plain-HTTP door, `CONNECT` and `egress.tcp` splices, and the AWS re-sign and mTLS bridge paths. Known gap: a dial the `egress.tcp` table refuses after a `CONNECT` was already answered with `200` (an address a CIDR deny covers, resolved from a name `egress.http` admitted) still closes the connection without the block response.
- The orphan reaper finds the children of the supervisor from `/proc/<pid>/stat`. Before, it read `/proc/<pid>/task/<tid>/children`, which a kernel without `CONFIG_PROC_CHILDREN` (such as a Kata Containers guest) does not have, and it then reaped no orphans.
- The orphan reaper also finds a child whose name is not UTF-8. The kernel cuts a name to 15 bytes, which can split a UTF-8 character, and the reaper skipped such a child, so its zombie stayed.
- The audit record of a request an intercepted session forwards now carries what the origin answered: `upstream_status_code`, the status of the final answer, and for a `4xx` with a JSON body of at most 16 KiB, `upstream_error_code`: the body's `error.code` (OpenAI's shape), or `error.type` in Anthropic's envelope (`{"type":"error","error":{...}}`). The body is read as it is relayed and reaches the workload unchanged; a compressed or longer body is not read. The proxy's own `status_code` is still not set on such a record, so a consumer can tell the proxy's decisions from the origin's answers. The record is sent when the answer's head arrives (for a `4xx` it reads, when its body ends), or with no answer when the origin gives none. A request an `llm` route translated, the plain-HTTP door, the mTLS bridge and the AWS re-sign path are not changed.
- A request an intercepted session forwards is sent once more when the origin refuses it `401` and a header credential it carried has another value since it was sent, as when the host renews a key its issuer retires at once. The second answer is relayed whatever it is, so a request is sent at most twice. It is sent again only when the proxy still holds all of it: no body, or a body it read whole for a rule; no credential in the body; no upgrade or `llm` translation; no interim answer already relayed to the workload; and a connection it can open again (a direct dial, or a tunnel it opens on demand). Its audit record has `metadata.resent_after_renewal: true` and the second answer's status.
- A `CONNECT` the proxy relays without intercepting it dials the destination before it answers. When the dial fails (the name does not resolve, the address refuses or cannot be reached, or an `egress.tcp` rule refuses the resolved address), the client gets `502 Bad Gateway` with a one-line `text/plain` body naming the target and the error, instead of a `200` and a tunnel that closes, which curl reported as a broken pipe and Python as an SSL EOF. An `egress.tcp` splice that cannot dial says the same. A failed dial on the `CONNECT` door, to the destination or to the upstream proxy, is logged at `warn`. A `CONNECT` the proxy intercepts (MITM, the AWS re-sign path, the mTLS bridge) still answers `200` first: it accepts the client's TLS inside the tunnel, and dials only once it has read and judged the request.
- A refused HTTPS request is audited with its method and path. A `CONNECT` or transparent TLS connection that `egress.http` refuses (`policy-deny`, `binary-not-allowed`) or the upstream proxy refuses (`upstream-policy`) gets one `failure` event, sent once the proxy has answered the request head it read inside the TLS session: `method` is the request method, `path` the path without its query, with any credential placeholder redacted as in the block body and cut to 256 bytes on a UTF-8 boundary, and `action` is `<METHOD> https://<host><path>`. When no head is read (the client does not start TLS, sends nothing within 2 s, does not trust the sandbox CA, closes, or has not sent a request within the 10 s bound, or no certificate can be made for the host), the event is the one sent before: `method: "CONNECT"` and no `path`. `host`, `result`, `status_code`, `metadata.reason` and the actor fields do not change, and the audit dedup counts each method and path apart. For Lens Agents and any consumer that counts these events: the event now comes after the TLS handshake and the answer, not when the `CONNECT` arrives, so milliseconds later and at worst 10 s. The answer to the workload does not change. A declined card is still audited by the answer, and an `egress.tcp` refusal and a refusal on the absolute-form `https://` door still name the destination only. No policy schema, wire type or protocol date change.
